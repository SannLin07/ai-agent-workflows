# Coding rules

- Keep each change focused on the requested behavior and the selected architecture.
- Prefer clear names, small cohesive functions, and explicit dependencies over clever abstractions.
- Keep UI rendering separate from business decisions and external I/O.
- Match the style and conventions already established by the consuming project unless a documented decision changes them.
- Do not add an abstraction, package, or generated layer without a concrete use in the task.
- Preserve accessibility semantics and provide meaningful loading, empty, success, and failure states where a user-facing flow needs them.
- Update relevant documentation when public behavior, setup, or decisions change.
